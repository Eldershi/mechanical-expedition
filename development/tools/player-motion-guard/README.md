# Player motion guard and local diagnostics

Version 1.1.0 is an optional server-side Forge 1.20.1 add-on. It protects player collision queries and keeps bounded local player/performance evidence under the server working directory's `expedition-diagnostics/`. Clients do not need this JAR. No service upload is performed.

Three cancellable HEAD injections guard `Entity.setDeltaMovement(Vec3)`, `Entity.move(MoverType, Vec3)` and `Entity.collide(Vec3)`. Mixin application priority 500 places the guard, cancellation check and early return before Alex's Caves' priority-1000 collision callback; the build verifies both real mixins together. The double-coordinate setter delegates to the Vec3 setter. The final collision check also covers argument changes inside `move`, including stuck-speed multiplication and edge handling.

A query is rejected if motion or original/swept bounds contain non-finite values, the original box is inverted, swept horizontal bounds exceed ±30,000,000, vertical bounds cannot be converted safely to the integer collision cursor, or the conservative three-dimensional section count reaches 4096. Query margins are X/Z ±2 blocks plus epsilon and Y −4/+2 blocks plus epsilon. Products saturate using division before multiplication. This bounds collision work rather than setting an equipment speed limit or a world build-height limit. Rejection directly clears velocity without recursive setter calls. It cancels `move` or returns zero from `collide`; an already-invalid bounding box remains blocked until an operator or another valid game mechanism repairs the position/bounds.

Each tracked server player has a bounded immutable state ring: tick/time, UUID/entity ID, dimension, position, motion, bounding box, rotation, pose, flags, fall distance and equipment version/capture tick. Default capacity is 1200 samples per player and 32 players. Every ten pending samples, or the configured persistence interval if earlier, are offered as a `state_batch`; normal disk history therefore contains per-tick samples rather than only one sparse state each second. Logout, shutdown and history eviction also flush pending samples. Player identity events associate UUIDs with GameProfile names on first observation, login and approximately every five minutes of healthy ticks.

Equipment/Curios selected IDs, counts, damage, enchantments and attribute modifiers are checked every 20 ticks and on important events, with entry/string limits. CarryOn reads selected fields from its actual synchronized data without copying or serializing carried container/entity NBT. Equipment snapshots are versioned and timestamped; a referenced capture tick may precede an action. High-frequency world actions reference the latest equipment version instead of rescanning every Curios slot for each block.

The timeline records login/logout, respawn, dimension changes, connection-level teleport requests with relative flags, damage/death, player kills, observed block breaks/placements, item toss/pickup and container opening/closing. Container events describe interaction, not individual slot transfers. Forge action events can precede the final result or later cancellation, so their observed values are retained as observations. CarryOn placement includes the actual carrying state separately. The recorder stores neither complete inventories/packet payloads nor a database for rollback.

Unsafe motion records preserve the first attempted values, current state and caller stack before rejection, with per-player repeat counts and 20-second detailed-event limits. A global ten-second admission gate coalesces expensive incident captures before thread/ring copying; suppressed captures are counted. The independent daemon watchdog observes main-thread tick progress and can capture a stall without waiting for a tick-end callback. Incidents prioritize the affected player's ring and use newest-first sample order within each player, with this order declared in the header. Thread collection scans at most 4096 IDs and records at most 128 threads ×64 frames, with truncation counts. ServerStopping/ServerStopped also capture non-daemon threads without forcing JVM exit or changing shutdown behavior.

The JSONL writer uses a bounded queue of at most 32 KiB encoded records (2048 default slots, at most 64 MiB queued payload). Producer-side encoding/admission performs no filesystem I/O. One daemon performs writes, file rotation and periodic force; defaults are an eight-MiB event file, sixteen event files and 128 MiB total event storage, plus eight incident files/32 MiB. Retention is capacity-based and its time span varies with activity. Queue refusal, oversize input, write failures, lost accepted records, retention deletion, incomplete recovered tails and truncated/suppressed incidents have separate counters. Existing complete lines survive restart; an incomplete old tail is preserved but counted and should be ignored by readers.

A force request is not a completed acknowledgement. `state.json` is published only after event data and the new marker file have been forced and the marker atomically replaced. `lastProcessedSequence` includes processed failed records; `lastSuccessfullyWrittenSequence`/`lastWrittenSequence` report completed writes, while `lastForcedSequence` reports the highest record confirmed in an actually forced file. `firstLostSequence` identifies a failed accepted write. If an I/O failure abandons a file containing earlier unconfirmed writes, `firstUnconfirmedClosedFileSequence` and `unconfirmedClosedFileRecords` expose that separate uncertainty; forcing a new empty file does not confirm the abandoned file. `lastContiguousForcedSequence` is the safe prefix watermark accounting for both gaps. Check the requested target against that contiguous watermark, `forceCount` and all loss/error counters. Oversize records rejected before queue admission do not acquire an accepted sequence. A failed marker replacement does not publish a new acknowledgement. Writer shutdown timeout is explicitly reported rather than described as fully persisted.

Only completed force-confirmed records/snapshots are acknowledged across process termination. Pending samples, queued records, in-progress files and changes after the latest marker can be lost; loss counters themselves may not yet have been forced. This is not zero-loss recording or a hardware power-failure guarantee. The supplied deployment configuration forces every second, with additional queue/backlog and capture/batch delay; the built-in fallback remains five seconds. Keep the server working directory on persistent storage.

JFR uses Java 17's default low-overhead settings with a 30-minute/256-MiB recording, Minecraft tick/network summaries, chunk generation events lasting at least 10 ms and world-load events. It excludes per-packet events. A daemon first dumps after five seconds, then every minute and on admitted incidents. Forced completed snapshots and receipts stay under `jfr/`, bounded to eight files/768 MiB. The active JVM repository may use temporary storage; only completed snapshots in the working directory are acknowledged. Shutdown hooks and the temporary repository are not the durability boundary.

Spark integration requires the existing Spark mod and an explicit `backgroundProfiler: true` configuration. The intended `config/spark/config.json` settings are `backgroundProfiler: true`, `backgroundProfilerEngine: "java"` and `backgroundProfilerInterval: 20`; preserve unrelated existing settings. It invokes only the public local command `spark profiler stop --save-to-file`, first after about 45 seconds and subsequently every five minutes. Confirmation waits for the full 60-second observation window, exactly one new stable profile, bounded copy, force and atomic archive/receipt publication. Confirmed unique generated source files are deleted only after verification; ambiguous sources are retained and counted. Archives under `spark/` are bounded to eight files/128 MiB, with a 32-MiB individual limit. An unsuccessful or ambiguous export blocks further automatic commands instead of accumulating new source files. Resume requests a background preflight; the source directory must fit its 256-MiB budget and at most 512 scanned entries before another export is allowed. A single Spark-generated source can exceed that budget, so it is not an absolute source-directory size cap. Status distinguishes command requests, observed files, confirmed archives, deleted sources and blocked reasons. The stop command ends whichever profiler is active, so pause automatic exports before manual profiling.

Copy [the complete configuration example](config/expedition-diagnostics.example.json) to `config/expedition-diagnostics.json`, or let the add-on create defaults at server start. `enabled: false` disables recording threads/JFR/Spark integration while retaining the collision guard. Other fields are clamped to bounded ranges; malformed configuration disables diagnostics and reports its error.

Operator commands (permission level 2):

- `/expeditiondiagnostics status`: capture readiness, counters, writer watermarks and JFR/Spark confirmation state.
- `/expeditiondiagnostics flush`: request force and return its accepted sequence target; verify the marker/status afterwards.
- `/expeditiondiagnostics incident`: request a coalesced stack/ring/JFR incident.
- `/expeditiondiagnostics sparkpause`: pause automatic exports for ten minutes.
- `/expeditiondiagnostics sparkresume`: resume with a 45-second buffer.

Read recent local evidence without starting Minecraft:

```sh
python3 tools/player-motion-guard/tools/read_timeline.py \
  --root /path/to/server/expedition-diagnostics --player PlayerName --since-seconds 900
python3 tools/player-motion-guard/tools/read_timeline.py \
  --root /path/to/server/expedition-diagnostics --player player-uuid --since-seconds 900
```

Run `python3 tools/player-motion-guard/build.py` from the project root to compile a deterministic JAR, test twenty policy boundaries, apply the actual Minecraft Entity mixin, verify retained original methods and confirm AC callback order. It does not edit an installed instance. Build inputs use the existing Forge/Minecraft/ASM/Mixin libraries. The Forge fixture in `tests/forge/` exercises real player movement and wall/floor collisions in a new disposable runtime; its client input supplies only dependency JARs. Set `--runtime-root` and `--client` explicitly; `--libraries`, `--guard`, `--java` and `--javac` override the other inputs.

`tests/durable/test_durability.py --output /path/to/new-test-directory` verifies force-confirmed JSONL across SIGKILL, incomplete-tail restart, bounded rotation, oversize refusal, real closed-channel write failure, unconfirmed writes abandoned before reopening a new file (with and without an earlier confirmed prefix), and blocked receipt replacement. `tests/jfr/test_durability.py` exercises the real JFR snapshot boundary and retention/failure/restart behavior. Generated test worlds, profiles, logs and player data remain disposable local artifacts and are not publication inputs.

The [serial Forge benchmark fixture](tests/benchmark/README.md) compares controlled ten-player activity and combined recorder/JFR/Spark costs. Its Java workload matches the running benchmark source; its published runner changes only project-root discovery. Generated measurements and runtime data are not source assets.
